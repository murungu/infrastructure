What the live review found

1. The implementation is mechanically sound

The panel does not overflow. Its disclosure is a real button, mobile and tablet links meet the 44px target, and the supporting blocks remain correctly below the product grid. This is a hierarchy refinement, not a repair of Wireframe 22.

2. The panel still speaks the sample-catalog language

“Categories,” Computers, Apparel, Books, and Gift Cards do not align with “Shop categories,” “Shop by solution,” or the renewable-energy routes approved for the menu and homepage. Category names must still come from nopCommerce administration, not theme markup.

3. The active page is not visible

On /desktops, the Desktops link has no visual emphasis and no aria-current="page". The tree shows where the page sits, but not which route is active.

4. The desktop hierarchy consumes too much attention

Ten 44–54px rows make the 260px panel about 530px tall. Tiny square bullets and indentation communicate structure weakly while competing with the product cards. The new header and homepage already provide broad catalog discovery; this panel should provide compact lateral movement.

5. Tablet wastes available width

The 720px open panel uses one long column. A two-column touch grid can preserve 48px routes while reducing scroll depth and matching the tablet menu pattern.

6. Adjacent naming is inconsistent

The listing says “Manufacturers,” while Wireframe 22 and the storefront direction use “Brands.” Rename the resource/admin label consistently; do not patch only this page.

Recommended direction to approve

  1. Keep Categories, Brands, and Popular tags below the product grid on mobile and tablet. Keep the category panel in the desktop sidebar.
  2. Rename the panel “Shop categories” so it matches the header trigger. Use “Shop by solution” only for the image-led homepage section.
  3. Mirror the header menu’s full top-level taxonomy: Solar panels, Batteries, Inverters, Charge controllers, and Accessories. The homepage can remain a curated four-route subset. Keep all names and URLs model-driven from nopCommerce.
  4. Mark the current category with aria-current="page", semibold text, a soft structural background, and a 3px black edge. Do not use red as an active-state decoration.
  5. Remove decorative square bullets. Make the full row the link and keep every route at least 44px high with a visible black focus ring.
  6. Keep the phone disclosure closed by default. At 768px, render the top-level routes in two touch-safe columns. On desktop, use one compact vertical list.
  7. Keep this panel top-level only. If the exact current page is a top-level category, use aria-current="page". On nested category pages, mark its top-level ancestor as the current section with aria-current="location"; the breadcrumb owns the exact path. Do not add a second descendant disclosure tree here.
  8. Do not add “Shop all products” unless a real all-products route exists. If the existing search route is used, label it “Search products,” matching the shipped homepage behavior.
  9. Rename “Manufacturers” to “Brands” through the shared localization or admin resource so the header, listing, search, and footer do not drift apart.

Implementation boundary

This is a wireframe proposal only. No storefront implementation has changed.

After approval, keep changes inside src/Presentation/Nop.Web/Themes/ArityTheme. Prefer a theme-owned override of the category navigation component plus scoped rules in Content/css/arity.catalog.css and the existing disclosure behavior in Content/js/arity.catalog.js. Do not modify nopCommerce core.

The category list, hierarchy, links, and active category must remain model-driven. Render visible top-level entries from CategoryNavigationModel, not fixed theme slots or the separately curated homepage component. Keep its ordering and names aligned with the header’s MenuModel through shared admin category data. Replace Computers, Apparel, and other sample data in nopCommerce administration. The five labels in this wireframe represent that target admin data; do not hardcode them in the theme. Preserve ACL, store mapping, published-state, customer-role, and category nesting behavior.

Do not add per-category product counts unless the existing view model can provide correct counts after ACL, store mapping, and filters. A compact truthful list is better than plausible-looking stale numbers.
