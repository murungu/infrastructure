What the live review found

1. Secondary blocks push the page title below the fold

At 375px and 768px the “Manufacturers” and “Popular tags” blocks render at y=301 and y=351, while the “Desktops” heading starts at y=451. Customers meet supporting navigation before they know which category they opened. The layout places the whole side-2 column before center-2 in source order.

2. Category navigation disappears below 1001px

The Categories block is display: none at 375px and 768px. On phones, the only way to reach a sibling category is the header menu or the browser back button. The listing itself offers no lateral movement.

3. Sort and per-page controls are below the touch-target standard

Both selects are 32px high at every viewport. The per-page select is 50px wide. Arity uses a 44px minimum for interactive controls, applied already in the header, homepage, and footer work.

4. Mobile spends 1,715px of scrolling on three products

The single-column grid gives each card a 304px image and a 485px total height. A customer comparing panels or batteries must scroll a full screen per product, and cannot see two prices at once.

5. Empty ratings appear on products with no reviews

Every card renders a five-star row. Products with no reviews show five empty stars with the title “0 review(s),” which reads as a poor score rather than as missing data. Wireframe 20 already resolved this on the homepage: show ratings only when reviews exist.

6. The compare action is still on every card

Each card carries a compare button beside “Add to cart.” The homepage product card dropped compare during Wireframe 20 because Arity Shop has no compare journey. The listing page should match.

7. Desktop uses the legacy 980px wrapper

The catalog page is capped at 980px while the approved rail is 1216px at 1280px with a 1600px cap on wide screens. The consequence is visible: product images shrink to 197px on a 1280px screen, smaller than they are on a phone.

8. There is no result count and no result range

Nothing on the page states how many products the category contains. CatalogProductsModel already derives from BasePageableModel, so TotalItems is available without new server code.

9. Page gutters do not match the rest of the storefront

The catalog rail uses 19px mobile and 29px tablet gutters. The header, hero, homepage categories, homepage products, and footer all use 16px, 24px, and 32px. The listing looks visually misaligned against every section above and below it.

10. “Add to cart” renders uppercase

The theme uppercases the catalog button, while the rest of the approved work uses sentence case. The resource string is already “Add to cart”; only the presentation differs.

11. Sample catalog data remains generic

The page still shows Computers, Desktops, IBM, and Lenovo. This is an admin data problem, not a theme problem, and it should be corrected in nopCommerce administration rather than in markup.

Recommended direction to approve

  1. Put the category title first on every viewport, followed by a product count, the toolbar, and then the product grid. Move the supporting blocks below the grid on mobile and tablet.
  2. Use the approved rail: 16px mobile gutters, 24px tablet gutters, 32px desktop gutters, and a 1600px cap. On a 1280px screen this gives a 1216px rail instead of 980px.
  3. Use two columns at 375px, three columns at 768px, and three columns beside the desktop sidebar. Product images grow from 197px to about 273px on desktop.
  4. Give every control a 44px minimum height: sort, per-page, view mode, pager links, “Add to cart,” and the wishlist button.
  5. Show the per-page selector and the grid/list view mode only from the desktop layout, where they are useful. Keep sort available at every width.
  6. On mobile and tablet, expose categories, brands, and tags as accessible accordion buttons below the grid. Keep them as an always-visible sidebar on desktop.
  7. Keep “Add to cart” plus wishlist on the card. In the two-up mobile grid, give “Add to cart” the full card width and place the 44px wishlist button on the image corner, so the label never wraps. Remove compare from the listing card, matching the approved homepage card.
  8. Render ratings only when a product has at least one review. Never show an empty five-star row.
  9. Show “12 products” under the title, and “Showing 1–6 of 12” beside the desktop sort controls, both from TotalItems and the existing paging model.
  10. Use sentence case, Inter, black and white surfaces, hairline greys, square corners, no shadows, no gradients, and no decorative colour.
  11. Keep subcategory grids, featured products, category descriptions, filters, widget zones, AJAX paging, and view-mode switching model-driven. Correct catalog content in admin, not in the theme.
  • □ Title and count first, supporting blocks after the grid.
  • □ Two columns mobile, three columns tablet and desktop.
  • □ 1216px desktop rail with a 1600px cap.
  • □ 44px minimum on every listing control.
  • □ Remove compare; keep Add to cart and wishlist.
  • □ Ratings only when reviews exist.
  • □ Per-page and view mode on desktop only.

Implementation boundary

This file is a wireframe only. No storefront implementation has been changed.

After approval, implementation stays inside src/Presentation/Nop.Web/Themes/ArityTheme. The likely theme-owned overrides are Views/Catalog/CategoryTemplate.ProductsInGridOrLines.cshtml, Views/Catalog/_CatalogSelectors.cshtml, Views/Catalog/_ProductsInGridOrLines.cshtml, and a new Content/css/arity.catalog.css registered for catalog pages only. The existing theme Views/Shared/_ProductBox.cshtml already owns the card, so the compare removal and the review-count condition belong there.

Source order matters. _ColumnsTwo.cshtml renders side-2 before center-2. Prefer a CSS ordering solution in the catalog stylesheet over a theme copy of the shared layout, so other two-column pages keep their current behavior. If a layout copy proves necessary, it must live in the theme.

Keep nopCommerce behavior intact: AJAX product loading through CatalogProducts, the sort, per-page, and view-mode change handlers, pager handlers, filter partials, subcategory and featured product sections, and every widget zone. Do not modify nopCommerce core. Do not hardcode category names, product data, brand names, or counts.
